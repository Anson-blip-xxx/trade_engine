# 方向策略保护阶段接线

实现 `services/v2_directional_lifecycle.py` 的 `DirectionalProtectionStage`，
可直接作为 `TradingPipeline(protection=...)` 的实际组件，不再需要空操作替身。
默认禁写，账户与传输必须绑定 Binance SANDBOX FUTURES，无新开仓能力。

## 执行顺序与恢复

1. 恢复已登记的保护单及交易所原生平仓子单，查证成交后幂等落库。
2. 在绑定账户内扫描正式 S6/S8 v2 订单，只处理可能已提交的开仓及仍有账本敞口
   的已结束开仓。绝不撤销或冻结尚未发送的 PREPARED 计划。
3. 读取原始不可变策略决策恢复止损计划，冻结继续加仓，恢复/撤销开仓余量，
   再按现有受控安装器创建或查询保护单。创建和撤单均须显式 allow_writes=True。
4. 再次读取交易所全账户，与 PG 仓位、订单、保护事实核对。所有阶段有明确证据
   才返回 CLEAR；仅收到保护 POST 的 NEW 响应不能判定仓位已保护。

阶段有独立账户级互斥锁，底层交易操作继续使用原有账户锁。轮询位置保存于 PG
`directional-protection-stage-v1/cursor`；单笔异常会记录错误类别并推进游标，
重启后继续扫描，避免坏订单长期占满批次。注册保护恢复异常不跳过原始止损恢复。
返回 CLEAR 仍不是开仓授权，执行门禁必须另外验证账户、杠杆、保证金和信号期限。

## 修复排队计划阻断止损的问题

原覆盖检查将所有非终态订单视为未完成的交易所订单。两个标的策略同时登记后，
尚未发送的另一笔计划可能令已有仓位无法安装止损。

现在只有 PG 证明同时满足以下条件的订单豁免该项检查：

- OPEN；
- PREPARED；
- 无交易所订单 ID；
- 无任何成交记录。

SUBMITTING/UNKNOWN、待平仓单、有交易所 ID 或成交的异常 PREPARED 仍阻断。
交易所实际持仓、普通挂单、条件单和唯一归属的其他核验均未放宽。
事实增加 leg、has_fills，前后快照比较与提交前重复核验仍生效。

## 验证边界

隔离 PostgreSQL 集成测试覆盖多空原始止损、另一个标的排队计划、未发送计划
保持原状、默认禁写、远端保护缺失/账户读取失败、严格豁免边界、LIVE 拒绝、
阶段互斥、异常订单的重启公平扫描，以及保护查询故障不跳过止损恢复。

两条关键串联用例：

- 统一循环内实际 S3 → S6 → PG 决策/订单 → 注入确认成交 → 实际止损恢复/安装。
- 实际保护组件创建止损 → 模拟交易所触发并生成平仓单 → 原生子单识别 →
  CLOSE 成交落库 → 账本剩余为零；重启重跑不会第二次 POST 或重复记录成交。

交易所响应和开仓成交仍由 QA 注入。这些不是在线策略成交或财务结算证明。
自动策略退出/追踪止盈、通用结算/归因、实时上下文与统一部署仍待完成。
