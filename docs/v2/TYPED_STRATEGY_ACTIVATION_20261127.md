# 新策略 Testnet 开仓启用记录

## 授权和范围

用户于 2026-11-27 明确要求启动开仓。仅限当前 SANDBOX 绑定，不切换账户，
不启用 LIVE，不注入伪造交易信号，不把进程存活或隔离测试当作实际成交。
开仓前实际只读 API 已核验：无持仓、无普通/条件挂单、账户可交易。

## 启动前修正

- 冷历史分页不再每页物化、排序整个首代部署后信号与全部消费回执。
  改为七个独立索引 seek lane，先 LIMIT 再匹配来源。每个 lane 独立回绕；
  来源不匹配的空页仍推进物理游标，不能解释为全队列耗尽。
  旧游标安全重扫；首次部署边界、原有候选/回执/任务/决定/意图恢复不丢失。
- 增加 `20261127_strategy_history_seek.sql`。存量库使用事务外
  `CREATE INDEX CONCURRENTLY`，保留旧 hot 索引，不删除业务事实。
- 初次保证金预留覆盖冻结计划允许的整个价格窗口，防止允许范围内的微小
  价格变化被误判为需要扩大预留。预留后仍检查资金池和真实可用余额；
  提交前风险上限、止损风险及未知订单占用不放宽。
- 单资产账户可保留闲置的其他币钱包，但必须证明没有对应风险占用，
  这些余额绝不换算或计入 USDT 开仓资金。多资产模式、负余额、风险字段缺失、
  非 USDT 仓位或 USDT 总额不一致继续拒绝。
  口径依据 [Binance Account Information V3](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/account#account-information-v3-user_data)。
- 明确的 `NO_SETUP` 是正常扫描结果，不再误报消费故障；仍保留任务，
  不伪造终结回执。未知数据、未知原因和风险失败仍单独标记。

## 配置和激活协议

1. 原始 OFF generation 1 保留，不重建策略实例，不重置订阅边界。
2. 新部署配置采用原账户较严格的单笔止损风险上限 0.25%，保证金池最高 70%，
   单笔保证金最高 10%，组合止损预算仍由现有账户配置限制；初始杠杆 2 倍。
   杠杆安全消耗、价差、深度配置对齐既有更严格限制，不提高账户风险额度。
3. 使用版本化 `entry_controls.configure` 关闭旧 S6/S8 剩余额度分配器；
   由新 typed sizing 负责分配，账户硬风控全部保留。不能直接修改 state payload。
4. 正常停止 controller，确认旧 worker 退出，切换不可变 release，安装明确的
   `typed-strategy-active.env.example` 外部覆盖：双 entry=true、recover_paused=false。
   原暂停模板仍保持默认禁用。
5. 启动后先恢复原 epoch 的 DRAINING 管理，核验管理周期，再发布 ACTIVE generation 2。
   通过账户控制角色的 `ExecutionRoutes.request` 追加同绑定新 epoch；
   控制器执行实际覆盖检查、确认旧 worker 停止、再次检查后进入 ACTIVE。
6. 验证自然候选、订单、实际成交和保护；没有观察到的环节必须保持未验证。

普通服务重启仍采用现有安全语义：先恢复管理、不隐式授权 OPEN。
双 entry=true 不是持久自动恢复授权；恢复开仓需新的同绑定 route 请求。
本轮不把任意 DRAINING 自动提升为 ACTIVE，也不覆盖暂停、换账户或凭据轮换意图。

## 回滚

先撤销新开仓能力并保留管理。不得丢弃 UNKNOWN/SUBMITTING 订单、保护或结算记录。
正常停止后再切回兼容的保留 release；外部覆盖改回双 entry=false。
索引是加法迁移，无需删除；配置和部署都采用新版本审计，不能倒改历史。

## 独立发现：行情采集容量

现有 market hub 单线程串行，有限十分钟观察更新 2,112 次；528 个支持合约
平均约 150 秒轮转一次。固定最新分钟抽取 21 个合约，首次仅 6 个完整，
稍后同窗口 10 个完整；已充分落库的旧窗口 21 个全部完整。主要是末尾
1–4 分钟尚未落库，不是历史中段缺失；这些抽样不能当作全天比例。

本次不修改行情新鲜度、时间戳或请求预算。缺失合约保持 UNKNOWN、不得开仓，
由独立有界任务重试，不应阻止其他合约。后续容量工作应解耦采集/落库与旧
全窗口指标计算，评估批量读取和有界并发，同时保留管理/保护请求配额。
仅增加轮询或配额不足以证明解决；验收应包含全目录尾部延迟分位数、实际
吞吐和保护请求延迟，不以进程存活代替。
