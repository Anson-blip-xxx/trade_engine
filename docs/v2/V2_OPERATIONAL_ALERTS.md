# V2 行情故障持久告警

状态：独立 V2 代码接线，未安装服务，未连接 Telegram。不是生产切换许可。

## 数据与恢复契约

- `v2_operational_outbox` 保存不可变运维事件，独立于交易意图和资金 outbox。
  不为告警生成虚假订单；没有文件存储或 Redis 权威降级。
- 行情监督工厂默认使用 `MarketAlerts`。临时故障仅保存阶段和异常类名，
  按环境、阶段、类名、PG 时间五分钟桶去重。桶边界可能相邻两次通知，
  持续故障每个新桶可再通知；不是逐次故障日志，也不是人工确认队列。
- 每轮扫描不可变 candle delivery 审计。隔离已提交但进程在通知前崩溃，
  后续仍能重建 `CANDLE_QUARANTINED` 事件；保留原事件时间、原因、frame 身份。
  新环境恢复时，历史隔离提醒并不代表该行情仍然有效。
- `v2_operational_attempts`、`v2_operational_receipts` 支持并发领取、退避、
  租约接管与成功回执。SANDBOX/LIVE 使用隔离视图及固定消费者身份。
  发送失败不删除事件，不依赖人工及时介入，不允许告警触发交易或复活过期信号。
- 复用财务投影的投递算法，表名由代码内静态标识符选择，不接受外部 SQL 表名配置。
  原财务默认表及接口保持不变；需要同时回归其交易/投影测试。

## 状态与传输约束

监督返回 `alert_status=QUEUED` 只说明 PG 已确认记录，**不是送达**。
`alert_delivery` 另报 claimed/delivered/failed/superseded 数量；PG 不可用明确
返回 UNAVAILABLE。健康轮次也补发旧队列，不只在当前报错时发送。
直接构造无 `alerts` 的监督器仍支持旧即时通知端口，只有显式工厂接线使用持久路径。

`notify(event)` 接收稳定 event_id、environment、kind 及受控 payload，必须设置有限
网络超时，并以明确 True 表示接收成功。当前只有注入端口；没有 TG 凭据读取或发送。
发送成功而回执提交失败可能重复通知，交付语义是 **at-least-once**。
租约只隔离数据库回执，不能撤回已发往外部的网络请求；支持去重的接收方应按 event_id
去重。不能声称 Telegram 本身提供本设计所需的严格幂等发送。

## 发布前仍需完成

- 实际 TG/告警网关适配、端到端有限超时、凭据和收件人配置及隔离网络验收。
- 独立于 PG 与业务进程的存活/依赖监控：PG 故障时不可能依靠 PG 自己持久记录新告警。
- 调用方持续运行监督循环；停止/宕机期间不执行补发。当前未新增 systemd 服务。
- 保留治理、积压容量与告警风暴负载验收。本阶段没有自动删除历史记录。
- 本 SQL 是 greenfield schema，只在临时 QA 实例应用；不是生产迁移脚本。
