# 退出派生数值精度修复

## 故障与修复边界

INXUSDT 于 12:25 分三笔成交：7825 × 0.006322、799 × 0.006318、942 × 0.006318。
数量均是合法账本值，但加权均价在 Decimal 精度 100 下产生 102 位小数。
`DirectionalExitStage._trace` 原来直接将结果传给退出策略的 `amount` 校验，
触发字符串长度/NUMERIC(38,18) 域错误；12:25:58 起退出失败，进而阻挡新开仓。
部分平仓后的计划风险分摊也可能产生同类循环小数。

仅修改 `services/v2_directional_exit.py` 的派生输入边界：

- 计算仍使用独立的 Decimal 精度 100，不依赖调用者全局精度。
- 加权入场价超过 18 位小数时，以 HALF_EVEN 归一到 18 位。
- 剩余计划风险超过 18 位时向上取整，避免低估风险或正数下溢为零分母。
- 归一后仍经过原有 `amount(..., positive=True)` 严格校验。
- 不修改原始分笔成交、持仓数量、账本收益、下单精度、风控阈值、保护单或账户配置。

## v2：明确请求下的同账户带仓恢复

- 只处理 DRAINING 中的新恢复请求，必须是同一 registry 和同一凭据 binding_version。
  单纯进程重启仍然没有新开仓权限；不同账户或不同凭据版本仍走原来的全平/结清检查。
- 恢复端口必须显式接线；无此端口的调用者保持旧行为。通过原有 vault 解析当前绑定，
  仅发签名 GET；现场确认交易权限、仓位与账本一致、全部持仓的原生止损覆盖、无未知订单。
- 复用 AccountCoverageAudit：前后本地账本快照、夹读交易所仓位、保护单身份/方向/触发价
  和 close-all 等条款均检查；不能把“存在一个止损单”当作保护完整。
- 停止旧执行进程前后各核对一次覆盖证据。旧进程未确认退出时禁止创建新的执行者。
  第二次检查失败时恢复为仅管理；新执行者启动失败时也仅尝试恢复管理，不能自动再次授权开仓。
  失败进程无法确认退出时保留 BLOCKED，不额外拉起另一执行者。
- 成功后使用新 epoch 和新 worker token，旧执行身份失效；所有交易请求仍受原数据库锁、
  账户/凭据绑定、策略、资金、保护/退出/结算前置检查约束。
- 要求已有账户策略，不初始化或重置资金基线；原始持仓与订单不删除、不取消、不强平。
