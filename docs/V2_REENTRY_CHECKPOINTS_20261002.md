## 原始锚点与有界增量状态

`v2_core/reentry_checkpoint.py` 保留退出时的 ATR、结构边界、退出原因和价格，以及之后每根 K 线形成的回撤、恢复、失效状态。不会因为交易年代久远而另取近期行情作为新退出锚点，也不会按经过时间自动解锁。

- 种子只使用退出前已收盘 K 线；跨越退出时刻的那根 K 线不得证明退出后的修复。
- 每页严格连续；缺失、中途跳页、未来 K 线、损坏的状态摘要不能被接受。
- 仅保存滚动量能所需的小窗口及状态，不让内存随交易年龄增长。
- 输入使用逐根 K 线的有序摘要链。此摘要不同于旧研究器的整段输入摘要，证明中明确标记 `ORDERED_BAR_HASH_CHAIN_V1`。
- 检查点只代表市场证据，不持有资金预留、不产生订单许可。
- 原始规则未通过此次改造重新调参。差分测试逐段对照旧算法，检查多空、退出类型、任意分页、低调用方 Decimal 精度、机会 token 和结构失效。

`services/v2_reentry_checkpoints.py` 使用新增 PostgreSQL 表 `v2_reentry_checkpoints`。身份绑定账户、环境、币种、前笔交易、完整退出证据和结构参数。历史/策略变化产生不同身份，不继承旧证明。

数据库更新使用显式 version CAS。两个任务同时读到同一版本时，一个成功，另一个明确返回并发冲突；不采用最后写入覆盖。归档 I/O 期间不持有数据库事务或交易账户锁。数据库语句预算 2 秒、锁等待预算 500 毫秒。

检查点是可从归档重建的派生状态，允许受控 CAS 更新；订单、成交、资金、结算仍由原有不可变证据和台账管理，不改写历史。

## 信号消费与后台准备分工

同步消费者最多处理一页，默认 `entry.reentry_page_bars=120`，可配置 1～1000 根。尚未追到所需快照截止点时返回 UNKNOWN，不能直接使用半成品。已有当前检查点时无需重扫 ClickHouse 历史。

独立入口：`python -m services.v2_reentry_prepare_entry`。

- 默认关闭，需要显式配置 `V2_REENTRY_PREPARE_ENABLED=true`。
- 每次重新读取租户真正 ACTIVE 的 SANDBOX 路由，校验账户绑定版本和未退休状态；网页选中但未激活的账户不作为执行账户。
- 每批默认 4 个币种、每币种 2 页；分别有上界。按上次尝试时间轮转，失败也记录尝试，避免一个异常币种长期占住任务队列。
- 不加载币安密钥、不解密凭据、不调用下单、平仓或 TG。
- 新增 `v2_reentry_preparation_attempts` 只保存公平调度元数据。

迁移与运行模板：

- `db/migrations/20261002_reentry_checkpoints.sql`
- `deploy/v2-testnet/reentry-checkpoint-grants.sql`

- `deploy/v2-testnet/trade-v2-reentry-prepare.service`
- `deploy/v2-testnet/trade-v2-reentry-prepare.timer`

模板使用独立 Unix/PG 用户；只对新派生表授予写权限，对所需的路由、成交、策略状态表授予读取权限。没有订单/资金写权限或凭据表权限。系统服务限制为本机网络、15% CPU、256 MB 内存、60 秒运行期限；当前未安装这些模板，也未宣称线上 ACL 已验收。

## 专用行情预算与尾部时间对齐

`services/v2_reentry_archive.py` 不复用原来 10 秒读取超时的交易客户端。只在首次需要时建立独立连接；普通与托管执行器均负责关闭它。

默认连接超时 1 秒、接收超时 2 秒、服务端查询预算 1 秒、查询重试 0 次、单查询线程、最多 2500 行/2 MiB。超限抛错，不允许静默截断后当成完整行情。参数由有范围约束的 `V2_REENTRY_READ_LIMITS_JSON` 配置。

这些是各阶段预算，不是整个调用链必定在 1～2 秒内完成的保证；首次初始化及数据库读取也有开销。需要在正式候选进程里继续测量延迟分位数。

同步门禁对齐已经通过上游时效校验的 S3 行情快照，而非无条件要求墙钟最新一分钟必须已归档：

1. 记录 `market_cutoff_ms` 和结构评估实际使用的 `bar_cutoff_ms`。
2. `entry.reentry_max_bar_age_ms` 默认 90000，范围 60000～180000。证明有效期不得超过行情截止点加该上限，且仍受原上下文、信号、门禁证明有效期约束。
3. 如果后台检查点更近，使用更近的状态，不能为得到 READY 回退到旧状态。
4. 历史中段缺口仍然拒绝；5 分钟旧行情也不能按默认参数被当成新行情。
5. 最终提交再核对完整前笔退出证据，并应用当前收紧后的行情年龄上限。

## 分笔成交取价修复

线上只读检查发现 AGTUSDT 的末笔平仓时间戳对应同一订单的两种成交价格。原先按“价格不唯一”拒绝，会把正常分笔成交误判为未知。

现在只在末笔时间戳对应**单一平仓订单**时，按成交数量加权计算该组末笔成交价格，四舍五入到 18 位小数。不同平仓订单同刻成交仍作为歧义拒绝。测试使用不等量成交并经过隔离的记账、费用匹配与结算验证，防止误用算术平均。

## 为什么尚未发布

新增只读预检 `scripts/v2_entry_release_preflight.py` 通过 AST 读取 schema，不执行被检查 release 的代码。它检查的是列出的进程是否具有同一字段、默认值、类型和范围，**不是完整的服务发现器，也不是交易授权**。

实际运行：

```
python -m scripts.v2_entry_release_preflight \
  --candidate /home/ubuntu/.opencode/trade/trading_engine-v2 \
  --reader /opt/trade-engine-v2/execution-controller \
  --reader /opt/trade-engine-v2/account-admin \
  --reader /opt/trade-engine-v2/dashboard
```

结果 BLOCKED：现有进程的 schema 与候选不同，且也存在本轮之前的版本差异。这个结果说明不能直接把候选的新增策略字段写到现有进程，并不意味着当前生效配置已经故障。预检输出还包含未部署的 QUANT 等工作区差异，不能因此把所有工作区功能一并上线。

下一发布批次必须：

1. 从实际部署基线按白名单构造候选，不覆盖工作区中无关的进行中改动。
2. 安装并验证加法迁移和专用角色权限，先运行准备任务，不打开开仓门禁。
3. 补全所有策略读取/写入进程清单，统一兼容 schema；针对精确候选包重跑 QA，而非复用工作区成绩。
4. 冻结发布期间的策略写入，准备与旧 schema 兼容的回滚配置；仅把 flag 改回 false 不等于旧解析器能接受新增字段。
5. 在实际消费者时点核验行情年龄、检查点命中、UNKNOWN 原因、同步延迟与队列延迟，再灰度启用。启用后用自然信号验证订单、保护、退出与结算，不伪造交易来证明通过。

当前仍未完成精确候选发布及自然信号在线验收，不声称新规则已经改善收益。
