# Encrypted runtime binding — opt-in candidate, not deployed

`SystemdMasterKeys` resolves `v2-master-<key_id>` beneath the systemd credentials
directory. It opens directory/file descriptors without following symlinks, rejects
foreign ownership, exposed permissions, non-regular files and non-32-byte material.
It checks the actual descriptor's mount ID, requiring a read-only ramfs or tmpfs
with `noswap`. Ordinary disk files and swappable tmpfs are refused. Missing or
unreadable `/proc` metadata fails closed. There is no file/env fallback or secret
subprocess. Python memory cannot guarantee zeroization; process core dumps/swap
and host hardening still require deployment validation.

Encrypted source provisioning must use `LoadCredentialEncrypted`, not plaintext
`LoadCredential`. A delivered memory file cannot prove how its source was stored;
the unit, encrypted artifact, host/TPM wrapping policy and backup policy must be
audited separately. See the official [systemd credential documentation](https://github.com/systemd/systemd/blob/main/docs/CREDENTIALS.md).
The checked-in drop-in is an example only, not an installed configuration. No
host wrapping key or actual master has been generated by this development stage.

## Daemon candidate configuration

`V2_CREDENTIAL_SOURCE=vault` requires server-configured tenant/registry IDs and a
positive `V2_VAULT_BINDING_VERSION`; `CREDENTIALS_DIRECTORY` comes from systemd.
The resolver checks tenant plus full exchange/account/environment/product scope,
and holds the registry row against rotation while decrypting its referenced vault
version. Only SANDBOX is accepted. Missing records, scope/version mismatch, broken
ciphertext or missing master abort startup; they never invoke the legacy reader.

In this mode `--credentials` is a protected TG-only configuration file. Exchange
credential fields in that file are rejected even if not selected. TG's own secret
storage is not migrated here. The absent source setting preserves existing legacy
startup for backwards compatibility; any `V2_VAULT_*` settings without explicit
vault mode are rejected to prevent silently ignored migration configuration.

These checks prove logical binding, NOT venue identity, ownership or trade
authorization. They do not stop an already-running worker on later key rotation.
Pinned startup resolution is not an execution lease or a completed account switch.
New-account verification and full execution fencing remain mandatory before the
web control may activate B. Old A must retain its credentials while draining.

## Not completed by this change

- Provisioning/backup/recovery of encrypted master material on this host.
- Enrollment and encrypted import of the current account, preserving historical ID.
- Replacing the active runtime virtualenv with a tested crypto-enabled lock.
- Adapting every standalone signing/recovery entry point, not just daemon startup.
- Real signing acceptance, authenticated web mounting and A/B switching.
- Removal of original plaintext exchange keys and remediation of historical copies.

No service, credential file or production database was changed. No original key
was removed; deleting it before verified encrypted-path acceptance would endanger
management of remaining positions.

## QA

93 tests passed with the isolated cryptography 49.0.0 environment, covering master
file permissions, symlinks/size/mount identity, no-swap policy, account/tenant/env/
version mismatch, rotation invalidation, encrypted daemon composition, no fallback
even when legacy credentials exist, mixed notification-file rejection, existing
daemon/bootstrap and account switch/drain regressions. Real systemd encrypted
credential provisioning and signing with migrated production keys were not run.
